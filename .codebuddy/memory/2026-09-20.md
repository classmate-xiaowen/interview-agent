## 修复：Chroma 向量维度冲突（384 vs 1024）
- 报错：`Collection expecting embedding with dimension of 384, got 1024`。
- 根因：旧 `chroma_data/interview_chunks` 集合里残留 Chroma 默认 MiniLM **384 维**向量（之前代码没真用 OpenAI 向量时，Chroma 自己用默认模型嵌入过知识库）。当前 `embed_model` 实际产出 **1024 维**向量（用户并非用默认的 text-embedding-3-small/1536，而是配置了一个 1024 维的 OpenAI 兼容 embedding 模型）。
- 之前写的"维度自愈"逻辑里 `except: pass` 把检测异常吞了，导致没触发重建，直接拿旧 384 集合去 query → 维度错。
- 修复（3 个文件）：
  1. `backend/app/rag/store.py` 重写：`check_dimension_mismatch()` 单独做维度检测（无法判断时保守返回需重建）；`_get_collection()` 在 mismatch 时 `reset_collection()` 重建；`add_chunks`/`query_chunks` 增加对 "dimension" 错误的**运行时兜底**：重建集合后重试一次（query 重建后集合为空，返回空结果而非报错）。`reset_collection()` 显式 delete+get_or_create。
  2. `backend/app/services/knowledge_service.py` 新增 `reindex_all()`：遍历全部 InterviewRecord，先 `delete_chunks_by_record` 再 `_index` 重建向量（用于 embedding 模型变更后自愈）。
  3. `backend/app/main.py` lifespan 启动钩子：调用 `store.check_dimension_mismatch()`，命中则 `reset_collection()` + `knowledge_service.reindex_all()` 自动重建知识库索引，避免清空后检索为空。
- 注意：store 的维度判定是**动态的**（用 `len(embedder.embed([...])[0])`），与具体模型维度解耦。用户 embedding 维度以实际配置为准（观察到 1024）。换 embedding 模型后重启后端会自动重建索引。
- Lints 报告均为项目既有 basedpyright 噪声；`py_compile` 通过。未提交（按规范不自动 commit）。

## 修复：结构化输出 InterviewTurn JSON 被截断导致解析失败
- 报错：`pydantic ValidationError: Invalid JSON: EOF while parsing an object at line 1 column 6834`（instructor 解析 InterviewTurn 失败），出现在 `interview_harness.stream_answer` 的 EVAL 结构化调用。
- 根因：`llm.chat_structured` 调用 `instructor` 时**未设置 `max_tokens`**，DeepSeek 兼容接口默认输出上限较小；而 Evaluation 含 covered_points/missing_points/structure_feedback/expression_feedback/suggestions/corrected_answer 等长字段，评估较长回答时 JSON 写一半被截断 → EOF 解析失败。
- 修复（2 个文件）：
  1. `backend/app/services/llm.py`：`chat_structured` 增加 `max_tokens: int = 8192` 参数并透传给 create（核心修复截断）。
  2. `backend/app/services/interview_harness.py`：EVAL 的 `chat_structured` 调用包 try/except，解析失败（如仍被截断）时降级为默认 `Evaluation(score=60)`、不追问、references 为空，保证整轮对话不崩溃（日志 warning）。
- 验证：`py_compile` 通过；Lints 均为项目既有噪声。未提交。

## 修复：护栏误杀 + EVAL JSON 仍截断
- 现象：① 一条回答触发 `Tripwire: possible prompt injection` 打挂流（ERROR）；② 另一条 EVAL JSON 仍被截断（WARNING 兜底）。
- 根因1（崩溃）：`guardrails.input_guardrail` 黑名单含字面量 `"system prompt"`，候选人正常讨论 AI/提示词面试题时提到该词即被误判注入。`routers/chat.py` 的 event_stream 已 try/except 把异常转 error 事件，但护栏太激进导致正常输入被拦。
- 根因2（截断）：即便 `max_tokens=8192` 仍截断。结合 `llm.py` 注释"DeepSeek 默认开启 thinking 模式"——模型在 JSON 前先吐大量推理 token 吃光预算，留给 JSON 的空间不足 → EOF 截断。
- 修复（5 个文件）：
  1. `backend/app/config.py`：新增 `llm_disable_thinking: bool = True`（关闭思考链，把 token 留给有效输出）。
  2. `backend/app/services/llm.py`：新增 `_thinking_extra()`，在 `chat_structured` 与 `stream_text` 调用时透传 `extra_body={"chat_template_kwargs":{"enable_thinking":False}}`（受 `llm_disable_thinking` 控制）。
  3. `backend/app/services/guardrails.py`：收窄黑名单，移除泛义词 `"system prompt"`，仅保留明显注入句式（ignore previous instructions / 忽略前面的指令 等），降低误报。
  4. `backend/app/services/interview_harness.py`：`input_guardrail` 调用包 try/except `guardrails.Tripwire` → 返回 `{"type":"error",...}` 友好事件而非崩溃；EVAL 提示增加「篇幅控制」约束（corrected_text≤1.5倍、suggestions≤4条）减小 JSON 体积。
  5. `backend/app/routers/chat.py`：event_stream 增加 `ev["type"]=="error"` 分支，转发 harness 主动返回的 error 事件给前端并结束本轮。
- 验证：`py_compile` 通过；guardrails.py/chat.py 无 lint 报错。未提交。
- 注意：若实际模型不支持 `enable_thinking` 的 extra_body（非 DeepSeek），设 `LLM_DISABLE_THINKING=false` 即可；最坏情况 EVAL 失败会被 harness 兜底为默认评分(60)，不会崩溃。

## 修复：store 维度探测因 numpy 数组 `or` 求布尔报错 → 每次启动误判重建
- 现象：启动日志 `[store] 维度探测异常，保守判定需重建集合: The truth value of an array with more than one element is ambiguous...`，随后 startup 误判维度不匹配并 `reindex_all` 重建全部知识库（功能正常但每次启动都全量重嵌，浪费）。
- 根因：`store.check_dimension_mismatch` 第 42 行 `(peek.get("embeddings") or [None])[0]` —— Chroma `col.get(include=["embeddings"])` 返回 numpy 数组，`or` 会先求该数组的布尔值，对 numpy 数组求布尔直接抛 ambiguous truth value 异常，落入 except 分支"保守重建"。
- 修复：`backend/app/rag/store.py` 改为显式判空 `embs = peek.get("embeddings"); emb = None if embs is None or len(embs)==0 else embs[0]`，不再用 `or` 作用于 numpy 数组。
- 效果：修复后下次启动维度探测正常（已重建集合为 1024 维，与当前模型一致 → 不再误重建）；`reindex_all` 仅在真正维度变更时触发。
- Lints 均为项目既有 basedpyright 噪声；`py_compile` 通过。未提交。

## 架构分析：AI 部分采用 Harness 工程的必要性（结论）
- 交付物：针对用户提问的详细分析（4 方面 + 结论 + 适用边界），已在对话中给出。
- 核心结论：采用并**补全** Harness 是必要的，但须"适度"。
- 已落地（验证了收益，应保留）：结构化输出契约（instructor Mode.JSON）、确定性评分/难度校准（adaptation.py 纯函数、已单测）、输入+输出双层护栏（Tripwire）、会话持久化、轻量单类状态机。
- 最大缺口（应按里程碑补）：① 可观测回放/eval harness（当前仅 logging.info 一行，无 trace 落库/回放/回归集，对应需求 §3.4.7/NFR-8）；② Prompt 模板版本化 + Prompt Caching（llm.py 无 cache_control）。建议二期（脱敏）前补这两项。
- 适用边界（避免 over-engineering）：MVP 单机本地**不必**上 LangGraph 图编排/Checkpoint（内存状态机+DB 重建已够）；触发重型 Harness 的临界点 = 引入 ASR/脱敏新工具（需 Tool 注册表）/ 多模型路由（需分层护栏）/ SaaS 多租户（需 Checkpoint）。永远不要退回纯 prompt 约束或自主智能体式自由工具调用（直接击穿 NFR-7 与数据安全）。
- 现状对照事实：状态机是 if/elif 隐式机（非 StateGraph/Checkpoint）；`_retrieve` 是唯一工具且无注册表；输出护栏被拒时直接 raise（无净化/重生，未被 try 包裹）；12 个 test 文件已覆盖确定性层。
